# Legal Bulletins 资讯质量标准（v0.6）

对齐上游 [AIHOT](https://github.com/KKKKhazix/AIHOT) 的「预筛宽召回 + 评分 + 高门槛精选」三层结构，但**读者定位不同**：

> **科技优先、法律语境优先。** 读者是法律科技从业者——律所合伙人、法务总监、法律科技公司创始人。他们关心技术与资本如何改变法律服务，**不关心每天的法律实务动态**。

这条定位是 v0.4 起的核心，也是与 v0.3 最大的差别。

## 与 v0.3 的关键差异

| | v0.3 | v0.4 之后 |
|---|---|---|
| 预筛硬门 | AI **×** 法律交叉 | **AI 实质信号**；法律侧降为加权维度 |
| 评分器 | 正则规则（五轴近似） | 五轴注意力评分提示词（`references/selection-score.md`） |
| 评分执行位置 | 服务端 | **客户端**：Agent 读提示词自行打分，无需 API Key |
| 刊发分调整 | 在基础分上叠加 ±28/−22/+14 等十余处 | 不再对分数加减，仅保留摘要质量、破平局与跨期衰减 |
| 候选池 | 预筛+噪声门双重收紧，实测 7d 仅 3 条 | 预筛放宽为纯 AI 硬门，信源放开 P2，可抓取源 81 → 117 |
| 跨期重复 | 无处理，连续 6 期同批条目入选 | 刊发排序按往期出现次数分档衰减 |

## 定位：为什么纯法律动态要压到极低

v0.3 把「法律 × AI 交叉」设为硬门，结果是两头都错：通用科技新闻在进评分器之前就被挡掉，而带「智慧法院」字样的纯司法动态反而拿到高分。

v0.4 的口径：

- **AI 实质信号是硬门**，没有就不进候选池。纯法律动态（判决、立法、执法、律所人事、普法宣传）**一律不在关注范围**。
- **法律相关性不是硬门，是评分的 `leg` 轴**。通用 AI 新闻若能说清它改变法律工作的哪一段（合同审查、检索、尽调、代理、诉讼、合规、风控、法律交付方式），照样高分。
- 与法律服务、法律科技市场、法律监管**无传导路径**的通用科技（消费级应用、图像生成、游戏、推荐算法）压到低分。

## 什么算高质量

1. **AI 实质信号**：模型、Agent、算法、工具链的具体能力或产品变化，不只是标题出现「智能」二字。
2. **法律传导可讲清**：`leg` 轴拿分靠的是「改变了法律工作的哪一段」，不是话题沾边。
3. **实质变化**：产品发布与定价/可用性变化、融资并购、模型能力边界变化、基础设施开源、正式监管规则、可迁移的实务方法。
4. **可核对摘要**：摘要必须概括事实，禁止正文截断、作者栏、半截英文；涉及条文/判决时提醒回原文。

## 什么必须压住

服务端预筛只挡「与 AI 完全无关」和「厂商营销/招聘」两类。**下表的压分全部由客户端评分执行**，提示词里写的是硬上限条款：

| 类型 | 例子 | 评分上限 |
|---|---|---|
| 纯法律动态 | 与 AI 无关的判决、立法、司法解释、律所人事 | 不入选（`is_pure_legal` 判定） |
| 智慧法院口号 | 「某某法院启用 AI」但无产品形态与可核对数据 | ≤ 25 |
| 产业/算力软文 | 东西部算力互济、词元工厂、算电协同、智能算力规模 | ≤ 20 |
| 赛事/会议/宣传周 | 世赛 AI 赛项、网安宣传周、法律 AI 研讨会、论坛峰会 | ≤ 15 |
| 外交与政务空谈 | 「贡献中国方案」「共促全球人工智能健康有序发展」、部委常规智能化表态 | ≤ 20 |
| 纯安全攻防 | 蜜罐、越狱、众测通报（无法律落地） | ≤ 20 |
| 消费/娱乐科技 | AI 写真、游戏 AI、电商推荐 | ≤ 15 |
| 常规条文修订 | 条文小改、无实质变化 | ≤ 12 |

这些条目**会出现在候选池里**（池子大是刻意的），但拿不到高分。这样做的好处是：漏掉一条该挡的只是浪费一次打分，而挡掉一条该留的等于整期少一条内容。

## 实现落点

| 组件 | 作用 |
|---|---|
| `references/selection-score.md` | **五轴注意力评分提示词**：8 类内容类型、五轴定义、类型权重、噪声上限。客户端（Agent）读它逐条打分 |
| `SKILL.md` 核心工作流 | 拉`mode=all` 全量池 → 本地评分 → 套阈值（≥60 进简报 / 50–59 补位 / <50 丢弃） |
| `server/app/classify.py` | 宽召回预筛（只要求 AI 实质信号）、`is_pure_legal` 纯法律识别、规则版回退打分、入库门槛 |
| `server/app/edition.py` | 每日刊配额、官媒整刊限流、摘要质量、破平局、跨期重复衰减 |
| `server/app/enrich.py` | 答案先行摘要提示词 |
| `server/app/db.py` | `count_edition_appearances()` 从 editions 表统计往期出现次数；`last_edition_at` 列与幂等迁移 |
| `references/sources.v1.yaml` | 信源层级、渠道与抓取规则 |

**评分不在服务端执行**，因此不需要 `OPENAI_API_KEY`、`OPENAI_BASE_URL` 或任何模型调用配置。服务端只做机械预筛与入库，客户端自己打分——这既是省掉一层外部依赖，也是让评分提示词能被用户直接阅读和修改。

## 评分模型

五轴整数 0–10，按内容类型加权（每行权重和为 10，结果天然落在 0–100）：

`attentionScore = sig×w1 + nov×w2 + cred×w3 + leg×w4 + act×w5`

| 轴 | 含义 |
|---|---|
| `sig` | 在法律科技时间线上是节点还是脚注 |
| `nov` | 带来多少明确新认知 |
| `cred` | 材料内部对核心事实的证据强度 |
| `leg` | **对法律服务的实际传导（最重的一轴）** |
| `act` | 能否马上使用、学习或调整选择 |

内容类型：`legaltech_product`、`funding_ma`、`model_release`、`infra_tool`、`regulation`、`case_litigation`、`practice_method`、`analysis_insight`。

`model_release` 与 `infra_tool` 的 `leg` 权重刻意偏低（1–2）：通用技术本身不自动等于法律科技新闻。

## 阈值

| 阈值 | 值 | 作用 |
|---|---|---|
| 客户端入选 | ≥ 60 | 进候选简报，默认给 3–8 条，按分数降序 |
| 客户端补位 | 50–59 | 仅在候选不足时补位 |
| 客户端丢弃 | < 50 | 纯法律动态无论分多低都不入选 |
| 服务端入库 | ≥ 30（法律科技垂直源 ≥ 25） | 宽召回门槛，只剔除明显该丢的条目 |

服务端门槛低、客户端门槛高，是刻意的两层结构：服务端负责「别把池子搞小」，客户端负责「别让噪音进来」。

## 跨期重复与新鲜度衰减

问题背景：实测 2026-10-02 至 10-07 连续 6 期日报，入选的是同一批条目。池子扩到 127 个源之后这个问题只会更明显。

处理方式是**刊发排序时按往期出现次数降权**，不设硬性排除：

| 往期出现次数 | 额外扣分 |
|---|---|
| 0–1 次 | 0 |
| 2 次 | 6 |
| 3 次 | 12 |
| 5 次 | 18 |
| ≥ 8 次 | 24（封顶） |

「昨天或今天刚刊过」再额外扣 6 分，合计同样受24 分上限约束。

三条设计约束：

1. **只影响排序，不决定入选。** 真正的高分条目连出几期仍应被看到，只是不再排在最前面。
2. **分档而非线性。** 线性递增会在 3 次就触顶，之后 4 次与 12 次完全没有区分度，衰减等于白做。
3. **次数从 `editions` 表实时统计，不存累加计数。** 累加有两坏处：重编同一期会把计数刷高，清零重写又会抹掉该条目在其它期的记录。`editions` 是唯一事实来源，不会漂移。

新内容充足时，往期条目被完全挤出；池子不足时它们自然补位。既不空刊，也不硬塞。

## 校准提示

低分是正常输出。发现以下情况说明需要调整：

- 候选池很小（`mode=all` 拉到的条数不足 20） → 检查 `AI_SIGNAL` 是否漏了该领域常用词，或信源是否大面积 `status` 异常
- 通用科技新闻全部落选 → 检查 `leg` 轴是否被打分得过低，注意「改变了法律工作的哪一段」才是依据，不是话题沾边
- 纯法律动态混进简报 → 检查评分时是否执行了 `is_pure_legal` 口径，以及提示词里的硬上限条款
- 分数挤在 90+ → 类型权重或基线过高
- 同一批条目仍跨多期重复入选 → 看 `REPEAT_PENALTY_TIERS` 是否够狠，或候选池本身就没有新内容（后者要回去看抓取）

## 与 AIHOT Skill 的关系

- 通用 AI 日更仍由 `aihot` Skill（`aihot.news`）覆盖，但**本刊不再回避通用 AI**——只收录对法律科技有明确传导路径的那部分，两边不再抢同一批噪声稿。
